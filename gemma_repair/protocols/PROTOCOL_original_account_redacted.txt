Prospective Gemma paired test-repair study, version 1

Question
Does replacing a source annotation filter with compiled test discovery and an exact invocation contract change the quality of real Gemma test repairs after one feedback opportunity?

Cohort fixed before new inference
Five repair units from four already source-exposed historical commits. Jsoup controlCharactersAreEscaped, Commons Codec testDecodeEncodeStandard and testDecodeEncodeUrl, Commons Lang testInvokeMethod, and JFreeChart testEquals. Codec units share one commit. These are not five independent repositories or unseen validation. Collections is excluded because the changed target is an unannotated helper and would require a different helper-to-caller extraction experiment. Compress and CSV are excluded to avoid resource-dependent source closure expansion. No exclusion depends on new model output. CPU qualification must admit at least four units across three commits before GPU launch. Report every qualification failure.

Interface
The model edits one fixed Java method body through a JSON body field. Signatures, annotations, parameter-provider values and surrounding test scaffolding are fixed. Existing targets start from historical parent bodies. Newly added Codec target methods start with an explicitly authored TODO body. Parent helpers, relevant production API contracts, imports and requirements may be supplied. Target developer answer bodies are withheld. Non-target developer methods remain fixed for compilation, but only declared target and fixed control methods are invoked. This is a constrained test-repair agent, not the entire competition harness or an end-to-end TEBench regrade.

Pairing and feedback
Generate one initial patch per unit and seed. Feed the identical initial bytes to both graders. The released arm uses the retained source annotation predicate on the externally fixed method scope and native outcomes of selected tests. The repaired arm uses compiled annotation inventory and exact native invocation counts. Both share decoding, policy, compilation, production and native runner. A released empty selection is EMPTY and can receive feedback. Nonempty released pass is accepted by that arm even when it omits a declared target. Each arm gets at most one extra model response after a non-PASS verdict. PASS arms retain their initial patch. Both repair arms use the same seed increment and budget. Identical feedback prompts reuse one response, with shared provenance explicitly recorded. Model feedback contains only that arm's developer-production verdict, selected-method counts, native failures or deterministic compile/decode errors. It never contains fault-oracle outcomes. No sample is retried because of an undesirable scientific outcome. Malformed, rejected, truncated, timed-out and missing responses remain in the denominator.

Sealed finite oracle
After finalization, run each final target on developer production and a predeclared fault variant. Invoke only the target-owned test method, with the exact fixed count, so immutable control tests cannot confer adequacy on a vacuous target. A patch is oracle-qualified only if it fully passes developer production and has at least one assertion/test failure on the fault with complete invocation accounting and no failed container or abort. Compilation failure, timeout and harness failure never count as killing a fault. Jsoup and Lang faults restore compatible historical parent production files. JFreeChart restores only the historical parent equals body, preserving the new API. Codec faults are authored wrong-alphabet substitutions in the appropriate strict String decoder. These are explicitly authored faults, not observed real-world defects. Gold target bodies must pass developer production and kill their fault before inference. Vacuous targets must pass both variants and fail adequacy. Stale parent tests must miss the new behavior or fail the new implementation as applicable. Finite mutation adequacy is not exhaustive semantic correctness.
